# แบบร่างข้อมูลชุดตรวจจาก Edge AI

เอกสารนี้เป็นข้อเสนอสำหรับการเชื่อมอุปกรณ์ ยังไม่ได้สร้าง API รับข้อมูล ภาพ หรือฐานข้อมูลชุดตรวจ หน้าจอ `InspectionPreview` แสดงข้อมูลจำลองเฉพาะล็อตรหัส `DEMO-LOT-*` และไม่ใช่ข้อมูลอุปกรณ์จริง

## ลำดับข้อมูล

อุปกรณ์เลือกหรือได้รับรหัสล็อต → ชั่งตัวอย่างและถ่ายภาพ → รันโมเดลตรวจวัตถุ → ส่งภาพและผลตรวจพร้อมรหัสชุดตรวจ → server ตรวจสอบ บันทึก และให้หน้าล็อต query ตาม lot ID → ผู้ใช้ตรวจทานผล ก่อนนำไปประเมินต่อ

แนะนำให้แยกภาพลง object storage หรือที่เก็บไฟล์ และเก็บ object key, checksum, ชนิดไฟล์ และขนาดในฐานข้อมูล แทนการเก็บ path ของ Raspberry Pi ซึ่ง server เปิดไม่ได้ ต้องกำหนดวิธี upload, สิทธิ์เข้าถึง และนโยบาย retention ก่อนใช้งานจริง

## ข้อมูลที่เสนอ

- **InspectionRun**: ID ฝั่ง server, `deviceId`, `deviceRunId` ที่อุปกรณ์สร้างและไม่ซ้ำในเครื่อง, `lotId`, เวลาถ่าย/ชั่งพร้อม timezone, เวลารับข้อมูล, สถานะประมวลผลและสถานะตรวจทาน, ชื่อ/เวอร์ชันโมเดลและ class mapping version
- **Measurement**: น้ำหนักตัวอย่างและหน่วย (เช่น g), เวลาชั่ง, device ID, calibration/วิธีชั่ง และความชื้นถ้ามีจากเซนเซอร์ ระบุว่าเป็นค่าที่วัดจริงหรือประมาณ ค่าไม่ทราบให้เป็น null
- **InspectionImage**: ภาพต้นฉบับและภาพ overlay แยกจากกัน พร้อม object key, checksum, MIME type, ขนาดภาพ และเวลาถ่าย หากยังไม่ได้รับไฟล์ให้แสดงสถานะรอภาพ
- **Detection**: image ID, local object ID, class code, confidence, bounding box (พิกัดและขนาดภาพอ้างอิง) และ mask ถ้ามี หากนับข้ามหลายภาพต้องระบุวิธีติดตามวัตถุหรือใช้รหัสที่ระบุวัตถุเดียวกัน เพื่อไม่ให้นับซ้ำ
- **Review**: ผู้ตรวจ เวลา ผลตรวจทาน และเหตุผลที่แก้ไข เก็บผลคาดการณ์เดิมแยกจากผลที่คนยืนยัน เพื่อรักษาที่มา

จาก Track 2 หน้า 4 มี 7 คลาส: `good`, `shell`, `full_black`, `hull_husk`, `broken`, `parchment`, `immature` โดย Good เป็นเมล็ดดี ส่วนอีก 6 คลาสเป็นข้อบกพร่อง คลาสในเอกสารเป็นตัวอย่างและอาจเปลี่ยนในชุดข้อมูลจริง จึงต้องเก็บ version และ mapping ของโมเดล

## ตัวอย่าง payload ที่เสนอ

```json
{
  "schemaVersion": "1.0",
  "deviceId": "pi-demo-01",
  "deviceRunId": "run-20261110-001",
  "lotCode": "DEMO-LOT-001",
  "capturedAt": "2026-11-10T04:00:00Z",
  "model": { "name": "coffee-detector", "version": "demo-1", "classMappingVersion": "track2-example-1" },
  "sampleWeight": { "value": 350, "unit": "g", "measuredAt": "2026-11-10T03:59:50Z", "source": "scale-demo" },
  "images": [{ "imageId": "img-001", "originalObjectKey": "runs/run-001/original.jpg", "overlayObjectKey": "runs/run-001/overlay.jpg", "width": 1280, "height": 720 }],
  "detections": [{ "objectId": "obj-001", "imageId": "img-001", "classCode": "shell", "confidence": 0.92, "bbox": { "x": 100, "y": 80, "width": 45, "height": 39 } }]
}
```

ตัวอย่างนี้แสดงเพียง 1 detection เพื่ออธิบายรูปแบบ ไม่ใช่ข้อมูลเดียวกับตัวเลขบนหน้าจอ ทั้ง payload และภาพต้องตรวจสอบขนาด ประเภท ขอบเขตพิกัด หน่วยและ class code รวมถึงความสัมพันธ์กับล็อตก่อนรับเข้า ให้ใช้ `(deviceId, deviceRunId)` เป็น idempotency key เพื่อให้ retry ปลอดภัย และจัดการข้อมูล/ไฟล์ไม่ครบด้วยสถานะ ไม่สร้างผลตรวจซ้ำ

## วิธีคิดเปอร์เซ็นต์

ตัวอย่าง UI สมมติภาพเดียวและนับวัตถุหนึ่งครั้ง รวม 100 วัตถุ (Good 78, อีก 6 คลาสรวม 22): สัดส่วนรายคลาส = จำนวนคลาส ÷ จำนวนวัตถุทั้งหมด × 100; สัดส่วนข้อบกพร่อง = จำนวน 6 คลาส ÷ จำนวนทั้งหมด × 100 จึงได้ 22% ตามจำนวนวัตถุ ไม่ใช่ % โดยน้ำหนัก หรือ % เมล็ดทั้งหมดที่ชั่ง เพราะ Hull / Husk อาจเป็นเศษและไม่ใช่เมล็ด และการซ้อนบังทำให้โมเดลนับคลาดเคลื่อนได้ ถ้าตัวหารเป็นศูนย์ให้แสดงว่าไม่มีข้อมูลแทนการหาร

น้ำหนัก 350 g เป็นน้ำหนักตัวอย่างรวมที่สมมติวัดแยกจากกล้อง ไม่สามารถคำนวณน้ำหนักแต่ละคลาสจากจำนวนวัตถุได้โดยไม่มีวิธีวัดหรือแบบจำลองที่ผ่านการตรวจสอบ เก็บน้ำหนักต่อคลาสเฉพาะเมื่อมีการชั่งแยกพร้อมที่มาและหน่วย ห้ามเทียบหรือขยายผลเป็นน้ำหนัก defect ของทั้งล็อตโดยอัตโนมัติ

การจัดเกรดและ defect equivalence เป็นอีกขั้นตอนหนึ่งที่ต้องอิงมาตรฐานและวิธีสุ่ม/ตรวจที่ตกลงไว้ ผลโมเดลเป็นข้อเสนอให้มนุษย์ตรวจทาน ไม่ใช่ผลรับรอง

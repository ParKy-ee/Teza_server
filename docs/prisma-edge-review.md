# แบบร่าง Prisma สำหรับตรวจสอบก่อนเชื่อม Edge

Schema ที่เสนออยู่ใน `prisma/schema.prisma` การแก้ไขล่าสุดยัง **ไม่มี migration ที่พร้อมใช้งาน** และยังไม่ได้เปลี่ยนฐานข้อมูลจริง ไฟล์ `docs/prisma-edge-revision.draft.sql` เป็นผล diff สำหรับรีวิวเท่านั้น ไม่ใช่ migration ที่ควรนำไปรันทันที เพราะมีการลบคอลัมน์และเพิ่มคอลัมน์บังคับ ซึ่งอาจทำให้ข้อมูลสูญหายหรือล้มเหลวหากมีข้อมูลเดิม

Migration ก่อนหน้า `20261111000000_edge_inspection` ยังอยู่ตามเดิมและอาจยังรันได้ด้วย `npm run db:migrate` แต่จะสร้างโครงสร้างรุ่นก่อนหน้า ไม่ใช่ schema ฉบับล่าสุด **อย่ารันเพื่ออัปเดต schema ฉบับนี้** จนกว่าจะมี migration ที่ทบทวนและวางแผนรักษาข้อมูลแล้ว

## โครงสร้างที่เสนอ

- `DetectionEvent`: เก็บ event ID จาก Pi, device ID, batch ID, lot ID, image ID (ยังไม่บังคับ), จำนวนรวมและ `countsByClass`; `createdAt` ต้องกำหนดจาก `captured_at` ของ Pi และไม่มีค่าเริ่มต้นจาก server ใน ingestion กำหนดให้ `batch_id` ต้องตรงกับ `Lot.code` ทุกตัวอักษร หากไม่พบล็อตจะไม่บันทึก event
- `LotImage`: เก็บ JPEG bytes ใน PostgreSQL ระบุ lot, event และชนิด `source` หรือ `crop`; การลบล็อตที่มีภาพถูกจำกัดไว้โดย relation นี้
- `Detection`: เก็บ cropImageId บังคับ และ imageId ภาพต้นฉบับเมื่อมี พร้อม detection ID, `className` เป็น enum `CoffeeClass` 7 คลาส, status, confidence, bbox และขนาดจริง `lengthMm`/`widthMm` ที่เป็น null ได้
- `Measurement`: เหลือ batch ID, lot ID, sample ID, value และ `createdAt` ที่ server กำหนดเมื่อบันทึก ไม่มีชนิด หน่วย สถานะ หรือเวลาวัดจากอุปกรณ์
- `InspectionReview`: เก็บผลตรวจทาน event และ detection แยกจากผลโมเดลเดิม ผู้ใช้ยังไม่ได้สั่งลบ event ID ในตาราง review จึงคงไว้

## ผลกระทบที่ต้องตรวจสอบ

1. **ภาพต้นฉบับ:** payload Coffee Vision v2 ปัจจุบันส่งเฉพาะภาพ crop รายวัตถุ ไม่มีไฟล์ภาพต้นฉบับ จึงยังสร้าง `LotImage` ต้นฉบับและอ้าง bbox เพื่อแสดงบนภาพไม่ได้ ต้องเพิ่มการส่งไฟล์ต้นฉบับและเชื่อมกับ lot/image ก่อน หรือออกแบบสัญญาใหม่ ภาพ crop ไม่สามารถประกอบกลับเป็นภาพต้นฉบับได้
2. **หน่วยและสถานะ measurement:** ต้องตกลงชนิดและหน่วยเดียวที่ระบบจะใช้ล่วงหน้า ข้อมูลที่อ่านไม่ได้เป็น null ได้แต่จะไม่รู้ว่าเกิด error หรือ stale รวมถึงไม่ทราบเวลาวัดจริงหรือที่มาอุปกรณ์จาก row นี้
3. **ขนาดจริง:** `lengthMm` และ `widthMm` เป็นช่องที่ Pi อาจส่งจากการวัดจริงที่สอบเทียบแล้ว ไม่ได้คำนวณจาก bbox หรือพิกเซลในโค้ดปัจจุบัน และไม่มีหลักฐานว่าระบบปัจจุบันตรวจวัดขนาดจริงได้ การแปลงพิกเซลเป็นมิลลิเมตรต้องสอบเทียบและตรวจสอบกับอุปกรณ์/ระนาบที่ใช้งาน การเอาวิธีวัดและ calibration ID ออกทำให้ตรวจสอบย้อนกลับความน่าเชื่อถือไม่ได้
4. **event และการตรวจทาน:** detection อ้างภาพแทน event และ event สามารถอ้างภาพเดียวกันได้หลายรายการ โครงสร้างนี้ไม่ได้บังคับให้หนึ่งภาพเป็นหนึ่ง event หรือให้ detection ใน review อยู่กับภาพของ event เดียวกัน ต้องกำหนดและตรวจใน service
5. **retry และ traceability:** event ID ยัง unique แต่การลบ fingerprint ทำให้ไม่สามารถเปรียบเทียบเนื้อหาเมื่อส่ง ID เดิมซ้ำได้จาก schema นี้ และการลบ model/class map version ทำให้ตรวจสอบย้อนกลับรุ่นโมเดลและ mapping ไม่ได้จากฐานข้อมูล
6. **payload ยังเดิม:** MQTT validator ยังคงตรวจ v2 ตาม handoff เดิม การลบ field ใน DB ไม่ได้ทำให้ field เหล่านั้นหายจาก payload และ subscriber ยังไม่บันทึกข้อมูล ต้องออกแบบตัวแปลงและตกลงกับทีม Pi ก่อน
7. **migration:** การแปลงคลาสเป็น enum ต้องตรวจข้อมูลเดิม การเปลี่ยน capturedAt เป็น createdAt ต้องย้ายค่าก่อนลบ การย้าย detection จาก event ไป image ต้องสร้างภาพและ mapping ก่อนบังคับ imageId; diff ดิบทำสิ่งเหล่านี้ไม่ครบ

## โค้ดจัดการภาพที่เตรียมไว้

`mqtt/ingest.cjs` ตรวจ v2 payload แล้วค้น `Lot.code` จาก `batch_id` แบบตรงตัว ก่อนแปลง Base64 กลับเป็น JPEG bytes และเตรียมเก็บ event, ภาพ crop และ detection ใน transaction เดียว เมื่อไม่พบล็อตหรือ event ID ซ้ำ transaction จะล้มเหลว การส่งซ้ำจึงยังไม่ถือเป็น retry ที่ยืนยันแล้ว ฟังก์ชันนี้ **ยังไม่ได้เชื่อม subscriber** เพราะ migration ล่าสุดและ application ACK ยังไม่พร้อม

`GET /api/lots/{lotId}/images` ออกแบบไว้สำหรับดูรายการภาพและ detection ที่เกี่ยวข้อง และ `GET /api/images/{imageId}` คืนไฟล์ JPEG โดย API นี้ยังไม่มีระบบบัญชีหรือ authorization และยังต้องใช้ migration ที่เตรียมอย่างถูกต้องก่อนจึงใช้งานได้จริง

bbox จาก v2 เป็นพิกัดของภาพต้นฉบับ ไม่ใช่พิกัดใน crop แม้เก็บพิกัดไว้ได้ แต่ไม่สามารถวาดบนภาพ crop ได้อย่างถูกต้องโดยไม่มีข้อมูลแปลงพิกัดและภาพต้นฉบับ

ตรวจ schema ด้วย `npx prisma validate` เมื่อยืนยันแบบแล้วจึงจัดทำ migration ที่เหมาะกับสถานะฐานข้อมูลจริงและสำรองข้อมูลก่อนนำไปใช้
